## What it does

`pr` writes the body of a pull request from the work's primary sources: the ticket, the spec, the ADRs, and the commit messages. It produces body text and nothing else: no branch is pushed, no request is opened, no tracker is written.

The summary is never read back out of the diff. A diff tells a reviewer what changed, and they already have that open in front of them; the question they came with is why, and that answer only exists upstream of the code. So this skill starts from the issue or spec and works toward the diff, choosing the smallest visual that makes the point.

## When to reach for it

Type `/pr`, or the agent reaches for it automatically when you ask for a pull request body, a PR description, or help filling one in.

| Your situation | Reach for |
| --- | --- |
| The work is committed and you need the request body written | `pr` |
| You also want the branch pushed and the request opened | [submit](./submit.md), which calls this skill for the body |
| The request is open and review comments came back | No fore skill covers this yet; answer them directly |
| Nothing is committed yet and you want it built | [implement](./implement.md) |

## The body, part by part

Four parts, and the optional pieces are genuinely optional:

- **Summary**: the smallest view that makes the key point. Pseudocode, a call tree, a shallow file tree, a Mermaid sequence, or a targeted diff, matched to what the change is.
- **Evidence**: a before and after pair. Screenshots first when the change is visual; otherwise the failing test run next to the passing one.
- **Merge Danger**: a one-way or two-way door call, followed by the blast radius in a word. Hard-to-reverse changes are one-way doors; a cheap rollback makes a change two-way.

The visual guidance is reproduced almost verbatim from the `show-me` skill, aimed at a diff instead of a conversation; the attribution lives in this skill's CREDITS file.

## Common questions

**Why not just summarize the diff?**

Because the diff answers a question nobody is asking. A reviewer reading "changes X, Y, and Z" already sees that in the diff view; what they cannot see is why those changes exist, which alternatives were considered, and what was deliberately left out. That information lives in the ticket, the spec, and the commits, so the body is written from those and the diff is used only to pick the visual. A body generated by reading the diff back is also wrong about emphasis: it gives the most lines to the biggest hunks, which are rarely the point.

**Does it push the branch or open the pull request?**

No. It writes body text only and performs no git or tracker writes. To push and open the request, run [submit](./submit.md), which generates the body by calling this skill.

**Do I have to fill in every part?**

No. The Merge Danger description and blast-radius ramifications are optional, and many changes need no diagram at all. What stays required is the door call itself (one-way or two-way is always answerable) and at least one piece of evidence. A section that says nothing is worse than a missing section.

**Where did this skill live before?**

It shipped first in the in-progress bucket, excluded from the plugin and installed directly by people who wanted to test it. It moved into engineering once the shape had held up in use.

## It's working if

- The summary traces to the ticket or spec, and you cannot tell it was written by someone who only looked at the diff.
- The body leads with one small visual rather than a paragraph restating the change.
- Evidence shows a concrete before and after, not an assertion that it works.
- The body names a one-way or two-way door and a blast radius before anyone is asked to merge.
- Nothing was pushed, opened, or written to the tracker while writing it.

## Where it fits

`pr` is the body-writing step at the tail of the build chain, `grill-with-docs -> to-spec -> to-tickets -> implement -> submit`, reached through [submit](./submit.md) or on its own whenever only the text is wanted.

- [submit](./submit.md) is the closest neighbour: it owns the push, the request, and the closing references, and calls this skill for the body.
- [implement](./implement.md) builds and commits the work the body describes.

[guide](./guide.md) routes across the whole set when you are unsure which skill the situation wants.
